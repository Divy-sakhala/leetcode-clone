1. The 60-Second Pitch

Memorise this. It is the first thing you will be asked.

"I built a full-stack LeetCode clone — an online judge where users solve DSA problems in a browser code editor and get their code actually compiled and executed against hidden test cases."

The frontend is React 19 + Vite, styled with Tailwind + DaisyUI, with Monaco (the editor that powers VS Code) as the code editor. Global auth state lives in Redux Toolkit.

The backend is a stateless Express 5 REST API. It uses two databases: MongoDB via Mongoose for users, problems, submissions and video metadata; and Redis as a JWT blocklist, so that logout actually invalidates a token — which a stateless JWT cannot do on its own.

Code execution is delegated to Judge0 (via RapidAPI). I submit all hidden test cases as one batch, get back a list of tokens, then poll until every submission finishes, and aggregate the verdict, runtime and memory.

There are two extra features: an AI DSA tutor built on Google Gemini with a tightly-scoped system prompt so it only discusses the current problem, and editorial videos uploaded straight from the browser to Cloudinary using a server-generated signed upload, so large video files never pass through my server.

There is a role-based admin panel for creating, deleting and attaching videos to problems — and when an admin creates a problem, the server first runs the reference solution through Judge0 to prove the problem is actually solvable before saving it.

That last point — validating reference solutions before saving — is the single most impressive line in this project. Say it out loud.

The middleware chain — order matters

app.use(cors({
    origin: 'http://localhost:5173',
    credentials: true
}))
app.use(express.json());
app.use(cookieParser());
  • cors — the browser blocks cross-origin requests by default (5173 to 3000 is cross-origin because the port differs). origin whitelists the Vite dev server. credentials: true makes the server send Access-Control-Allow-Credentials: true, without which the browser refuses to attach the cookie. This must pair with withCredentials: true on the axios side — both halves are required.
  • express.json() — parses a JSON request body into req.body. Without it, req.body is undefined.
  • cookieParser() — parses the Cookie header into the req.cookies object, which every auth middleware reads.

Mounting the routers

The cascade-delete hook

userSchema.post('findOneAndDelete', async function (userInfo) {
    if (userInfo) {
      await mongoose.model('submission').deleteMany({ userId: userInfo._id });
    }
});

This is Mongoose middleware (a "hook"). post means it runs after the delete succeeds. It cleans up every submission belonging to the deleted user — MongoDB has no foreign keys or ON DELETE CASCADE, so you implement cascade yourself.

Key detail: User.findByIdAndDelete(id) internally calls findOneAndDelete, so this hook does fire from deleteProfile. It would not fire from deleteMany() or User.remove(). Hooks are tied to the specific query method — a very common interview question.

Note also mongoose.model('submission') is used instead of require('../models/submission') — this deliberately avoids a circular import between the two model files.

The compound index is a strong talking point. {userId:1, problemId:1} creates a B-tree index over both fields (1 = ascending). 5.2 Middleware — the authentication gates

middleware/userMiddleware.js
const userMiddleware = async (req,res,next)=>{
  try{
    const {token} = req.cookies;
    if(!token) throw new Error("Token is not persent");

    const payload = jwt.verify(token, process.env.JWT_KEY);
    const {_id} = payload;
    if(!_id) throw new Error("Invalid token");

    const result = await User.findById(_id);
    if(!result) throw new Error("User Doesn't Exist");

    const IsBlocked = await redisClient.exists(`token:${token}`);
    if(IsBlocked) throw new Error("Invalid Token");

    req.result = result;     // hand the user object to the controller
    next();                  // pass control down the chain
  }
  catch(err){ res.status(401).send("Error: "+ err.message) }
}

Five checks, in order — walk through them exactly like this if asked:

  1. Is a token present? Read from the cookie (not an Authorization header).
  2. jwt.verify — recomputes the HMAC signature with JWT_KEY and compares. This detects tampering and throws TokenExpiredError if exp has passed. This is the crypto step.
  3. Does the user still exist? A valid token for a deleted account must be rejected.
  4. Is the token blocklisted? redisClient.exists('token:<jwt>') — this is how logout works. An O(1) Redis lookup.
  5. Attach and continue. req.result = result makes the full user document available to every downstream controller, which is why controllers can just write req.result._id.
Why next() matters: Express middleware is a chain. Calling next() passes control to the next handler. Not calling it (and not sending a response) hangs the request forever. Here, any failure throws, is caught, and returns 401 Unauthorized — so next() is never reached on failure.
middleware/adminMiddleware.js

Identical to userMiddleware with one extra line:

if(payload.role != 'admin') throw new Error("Invalid Token");
Security flaw to flag proactively: the role is read from the JWT payload, not from the freshly-loaded database document. The token is signed so a user cannot forge it — but if an admin is demoted to user in the database, their existing token still grants admin access for up to an hour. The correct check is if (result.role !== 'admin'), using the DB value that was just fetched. Saying this unprompted is very impressive.

Also note both files are ~90% identical — a reviewer will ask why you did not extract a shared authenticate() and compose requireRole('admin') on top. Have that answer ready: "duplication I would refactor into one middleware factory."

Sends an array of submissions in one HTTP call. Each element is { source_code, language_id, stdin, expected_output }. Judge0 responds immediately with an array of tokens — it does not wait for execution. This is an asynchronous job queue pattern.

// response shape
[ {"token":"db54881d-bcf5-4c7b-a2e3-d33fe7e25de7"},

Why batch? A problem with 10 hidden test cases would otherwise be 10 separate HTTP round-trips. Batching makes it 1 submit + N polls, cutting latency and staying inside RapidAPI rate limits.

Step 2 — poll until finished

const submitToken = async(resultToken)=>{
  const options = {
    method: 'GET',
    url: 'https://judge0-ce.p.rapidapi.com/submissions/batch',
    params: { tokens: resultToken.join(","), base64_encoded:'false', fields:'*' },
    headers: { 'x-rapidapi-key': process.env.JUDGE0_KEY,
               'x-rapidapi-host':'judge0-ce.p.rapidapi.com' }
  };
  async function fetchData() { ... return response.data; }

  while(true){
    const result = await fetchData();
    const IsResultObtained = result.submissions.every((r)=> r.status_id > 2);
    if(IsResultObtained) return result.submissions;
    await waiting(1000);
  }
}

Joins the tokens into a comma-separated string and polls. The exit condition is status_id > 2 for every submission.

Judge0 status codes — memorise this table

idMeaningTerminal?
1In Queueno — keep polling
2Processingno — keep polling
3Accepted — output matched expectedyes
4Wrong Answeryes
5Time Limit Exceededyes
6Compilation Erroryes
7–12Runtime Errors (SIGSEGV, SIGFPE, NZEC, …)yes
13Internal Erroryes
14Exec Format Erroryes

So status_id > 2 is a neat way of saying "finished, whatever the outcome", and status_id === 3 means "this test case passed".

Real bug — the waiting() helper does nothing. 
const waiting = async(timer)=>{
  setTimeout(()=>{ return 1; }, timer);
}

setTimeout is not a Promise, and returning from inside its callback returns from the callback, not from waiting. So waiting resolves immediately and await waiting(1000) does not pause at all. The result is a hot polling loop that hammers Judge0 hundreds of times per second and can blow the RapidAPI quota.

The fix — know this by heart:

const waiting = (timer) => new Promise(resolve => setTimeout(resolve, timer));

Because await only pauses for a thenable, you must wrap the callback API in a Promise. This is the single best bug to bring up unprompted — it proves you understand the event loop, not just syntax.

5.4 Controllers

controllers/userAuthent.js — register
const register = async (req,res)=>{
  try{
    validate(req.body);
    const {firstName, emailId, password} = req.body;

    req.body.password = await bcrypt.hash(password, 10);
    req.body.role = 'user';

    const user = await User.create(req.body);
    const token = jwt.sign({_id:user._id, emailId:emailId, role:'user'},
                            process.env.JWT_KEY, {expiresIn: 60*60});
    const reply = { firstName:user.firstName, emailId:user.emailId,
                    _id:user._id, role:user.role };

    res.cookie('token', token, {maxAge: 60*60*1000});
    res.status(201).json({ user:reply, message:"Loggin Successfully" });
  }
  catch(err){ res.status(400).send("Error: "+err); }
}
  1. validate(req.body) — throws on bad input, caught below as a 400.
  2. bcrypt.hash(password, 10) — 10 is the cost factor: 2^10 = 1024 iterations. bcrypt generates a random salt and embeds it in the output, so two users with the same password get different hashes. It is deliberately slow to make brute-force expensive.
  3. req.body.role = 'user' — hardcoded, so a user cannot POST {"role":"admin"} and escalate privileges. (This is a mass-assignment defence — name it.)
  4. jwt.sign — payload contains _id, emailId, role. expiresIn: 60*60 = 3600 seconds = 1 hour.
  5. reply — hand-built response object so the password hash is never sent to the browser.
  6. res.cookie — maxAge here is in milliseconds (3,600,000), matching the token's 1-hour life. Note the unit difference from expiresIn.
  7. 201 Created — correct status for "a resource was created".
Missing cookie flags. The cookie should be { httpOnly:true, secure:true, sameSite:'strict' }. Without httpOnly, any injected JavaScript can read document.cookie and steal the token (XSS). secure forces HTTPS-only transmission; sameSite mitigates CSRF. This is the most important security gap in the project — volunteer it before they find it.

userAuthent.js — logout (the clever part)
const {token} = req.cookies;
const payload = jwt.decode(token);

await redisClient.set(`token:${token}`, 'Blocked');
await redisClient.expireAt(`token:${token}`, payload.exp);

res.cookie("token", null, {expires: new Date(Date.now())});
res.send("Logged Out Succesfully");
This is the best architectural idea in the project. Explain it like this:

A JWT is stateless — the server does not store it, it just verifies the signature. That means you cannot "delete" a JWT server-side. Clearing the cookie only helps an honest browser; anyone who copied the token still has a valid one until it expires.

So logout writes the token into a Redis blocklist, and userMiddleware checks that list on every request. Redis is used because the check happens on every single request and Redis is an in-memory O(1) key lookup — putting the blocklist in MongoDB would add a disk read to every request.

And the elegant bit: expireAt(key, payload.exp) sets the Redis TTL to exactly the token's own expiry timestamp. Once the JWT expires it would be rejected by jwt.verify anyway, so keeping it blocklisted is pointless — Redis evicts it automatically. The blocklist is self-cleaning and bounded in size. No cron job needed.

Note jwt.decode (not verify) is used here — it only reads the payload without checking the signature. Fine in this spot because userMiddleware already verified the token before the route ran.

Why signed direct upload — a genuinely senior-level pattern.

A 100 MB video could be uploaded to my Express server, which then forwards it to Cloudinary. That doubles bandwidth, ties up a Node process (which is single-threaded) for minutes, and risks memory pressure.

Instead the server only issues a short-lived cryptographic signature — an HMAC of the upload parameters signed with the API secret. The browser then uploads directly to Cloudinary, presenting that signature. Cloudinary recomputes the HMAC and accepts the upload only if it matches.

The result: the API secret never leaves the server, the file never touches my server, and I still fully control what may be uploaded (the public_id path and timestamp are fixed by me and are part of the signed payload, so the client cannot tamper with them).

    } catch (error) {
      return rejectWithValue(error);       // -> becomes action.payload on .rejected
    }
  }
);

createAsyncThunk takes a type prefix and an async function, and automatically generates three action types: auth/login/pending, /fulfilled, /rejected. You never write those by hand.

rejectWithValue matters: a plain throw puts the raw Error in action.error, whereas rejectWithValue(x) puts your chosen value in action.payload — giving you control over the error shape.

export const checkAuth = createAsyncThunk('auth/check', async (_, {rejectWithValue}) => {
    try {
      const { data } = await axiosClient.get('/user/check');
      return data.user;
    } catch (error) {
      if (error.response?.status === 401) return rejectWithValue(null);  // no session
      return rejectWithValue(error);
    }
});

The 401 is special-cased: "not logged in" is a normal state, not an error to display. The underscore is the unused arg parameter — thunks always receive (arg, thunkAPI).

The slice

const authSlice = createSlice({
  name: 'auth',
  initialState: { user:null, isAuthenticated:false, loading:false, error:null },
  reducers: {},                 // no synchronous actions needed

    builder

      .addCase(loginUser.fulfilled, (state, action) => {

8. Core Concepts Explained

These are the "why", not the "what". Expect at least five of these to come up.

8.1 JWT — how it actually works

A JWT is three base64url segments joined by dots: header.payload.signature.

header    {"alg":"HS256","typ":"JWT"}
payload   {"_id":"665...","emailId":"a@b.com","role":"user","iat":...,"exp":...}
signature HMACSHA256( base64(header) + "." + base64(payload), JWT_KEY )
Critical point most candidates get wrong: the payload is encoded, not encrypted. Anyone can paste the token into jwt.io and read it. The signature guarantees integrity (nobody can change the payload without the secret), not confidentiality. So never put secrets in a JWT payload — which is why this project puts only _id, emailId and role in it.

Verification is: recompute the HMAC over the received header+payload using JWT_KEY, compare with the received signature, then check exp. If either fails, jwt.verify throws.

8.2 The Redis blocklist — the project's smartest idea

Stateless JWT has one real weakness: you cannot un-issue a token. This project solves it in three lines:

await redisClient.set(`token:${token}`, 'Blocked');
await redisClient.expireAt(`token:${token}`, payload.exp);
// and in userMiddleware:
const IsBlocked = await redisClient.exists(`token:${token}`);
  • Why Redis and not MongoDB? This lookup runs on every authenticated request. Redis is in-memory with O(1) key access (microseconds); Mongo would add a disk-backed query to every request.
  • Why expireAt(payload.exp)? After the JWT's own expiry, jwt.verify rejects it anyway, so the blocklist entry is dead weight. Setting the Redis TTL to exactly exp makes the blocklist self-pruning and permanently bounded — you never need a cleanup job, and memory cannot grow unbounded.
  • Trade-off to acknowledge: this reintroduces server state, so it is a hybrid. A fully stateless alternative is short-lived access tokens (5–15 min) plus refresh tokens, which shrinks the revocation window instead of eliminating it.

8.3 bcrypt and password storage

$2b$10$N9qo8uLOickgx2ZMRZoMye.IjZAgcfl7p92ldGxad68LJZdL17lhWy
 |  |  |                     |
 |  |  +-- 22-char salt      +-- 31-char hash
 |  +----- cost factor 10 = 2^10 = 1024 rounds
 +-------- algorithm version
  • Hashing, not encryption — one-way by design; there is no "decrypt".
  • The salt is random per password and stored inside the hash, which is why two identical passwords produce different hashes and rainbow tables are useless.
  • Deliberately slow. Unlike SHA-256 (designed to be fast), bcrypt's cost factor makes each guess expensive, so offline brute-force is impractical. Raising the cost by 1 doubles the work.
  • bcrypt.compare(plain, hash) extracts the salt from the stored hash, re-hashes the input, and compares in constant time.

8.4 Judge0 and the async job pattern

Compiling and running untrusted code takes seconds and must be sandboxed — you can never eval() user code in your own Node process. Judge0 runs each submission in an isolated container with CPU, memory and wall-clock limits.

Because execution is slow, the API is asynchronous:

  1. POST batch → returns tokens instantly (a receipt, not a result).
  2. GET batch?tokens=... → poll until status_id > 2 for all.

This is the classic submit-and-poll job queue. If asked "how would you improve it?", the answer is webhooks/callbacks (Judge0 supports callback_url) or moving judging into a background worker with BullMQ + Redis, so the HTTP request returns a submission id immediately and the frontend subscribes via WebSocket or Server-Sent Events. That removes the long-held HTTP connection entirely.

8.6 CORS, in one paragraph

The browser's same-origin policy blocks JS on localhost:5173 from reading a response from localhost:3000 — different port means different origin. CORS is the server opting in via response headers. Three rules to remember: (1) origin must be an explicit URL, because * is illegal with credentials; (2) credentials:true on the server and withCredentials:true on the client are both required or the cookie is silently dropped; (3) non-simple requests (PUT, DELETE, JSON bodies) trigger a preflight OPTIONS request first, which the cors middleware answers automatically.

Security

  • Cookie flags — no httpOnly, secure or sameSite (see above). Highest-impact single fix.
  • Admin role read from the token, not the DB — adminMiddleware checks payload.role. A demoted admin keeps admin rights until the token expires. Use result.role.
  • referenceSolution is sent to every logged-in user via getProblemById's projection — users can read the answer without solving. Gate it behind an accepted submission.
  • No rate limiting anywhere. Login is brute-forceable; /ai/chat and /submission/* cost real money per call. Add express-rate-limit, tighter on auth and AI routes.
  • No Helmet — missing standard security headers (CSP, HSTS, X-Frame-Options).
  • Errors leak internals — res.status(400).send("Error: "+err) stringifies the whole error, exposing stack details and Mongo error text. Log server-side, return a generic client message.
  • No CSRF protection — cookie auth without sameSite is CSRF-exposed.
  • Video delete ignores ownership — findOneAndDelete({problemId}) lets any admin delete any admin's video.

Correctness

  • login has no null check on User.findOne — a nonexistent email throws a TypeError that the catch block disguises as a 401.
  • submittedProblem sends two responses when there are no submissions → ERR_HTTP_HEADERS_SENT, and returns a string in one branch and an array in the other. Always return [].
  • solveDoubt calls main() without await → Gemini failures become unhandled rejections and the client hangs.
  • getAllProblem returns 404 when the list is empty — an empty collection is a valid 200 [], not "not found". It breaks the Homepage.
  • ProblemPage .find(...).initialCode throws if a language template is missing.
  • Switching language wipes typed code — no per-language draft.
  • Difficulty badges always red in the admin tables — comparing 'Easy' against the stored 'easy'.
  • Video thumbnails never render — cloudinary.image() returns an HTML <img> tag, not a URL, so poster={thumbnailUrl} gets markup. Use cloudinary.url() (already commented out in the file).
  • user.role without optional chaining in the Homepage navbar.
  • /admin/update card links to a route that does not exist — the backend PUT /problem/update/:id has no UI.

Architecture & scale

  • No pagination — getAllProblem returns everything and the browser filters. Move filtering/paging to the server.
  • Long-held HTTP connections while polling Judge0 — a submission blocks a request for seconds. Move judging to a background worker (BullMQ) and push results over WebSocket/SSE.
  • No caching — Redis is used only as a blocklist. The problem list is read-heavy and near-static; cache it.
  • No tests at all — no Jest/Supertest for the API, no React Testing Library. Usually the first thing a reviewer notices.
  • No centralised error handler — every controller repeats try/catch and formats its own errors. One Express error middleware plus a custom AppError class would remove that duplication.
  • Duplicated middleware — userMiddleware and adminMiddleware are ~90% identical; compose authenticate + requireRole('admin').
  • Duplicated Judge0 validation in createProblem and updateProblem — extract validateReferenceSolutions().
  • Three names for one language (cpp, C++, c++) patched with ad-hoc string rewrites. Normalise on one canonical identifier.
  • Hardcoded URLs — localhost:3000, localhost:5173 and the Redis host are baked in. Move to env vars before deploying.
  • No lastName/age collected anywhere despite being in the schema; getProfile is commented out.

10. Interview Q&A — 40 Questions

A. Project & architecture

1. Explain your project in two minutes.
Use the pitch from Section 1. Structure: what it does → frontend stack → backend stack → the two databases and why → Judge0 for execution → the two extra features (AI tutor, videos) → the admin panel with self-validating problem creation.
2. Why did you use two databases?
Different access patterns. MongoDB is the durable store for documents with flexible, nested shapes — a problem has arrays of test cases and per-language code templates, which map naturally to documents. Redis holds one thing: the JWT blocklist, which is read on every authenticated request and needs microsecond O(1) lookups and automatic TTL expiry. Using the right tool for each job rather than forcing both into one.
3. Why MongoDB rather than PostgreSQL?
The core entity is deeply nested and variable — visible and hidden test cases, three language templates, three reference solutions. In SQL that is four or five join tables; in MongoDB it is one document read with no joins. The relationships that do exist (user → submissions) are simple. That said, I would consider Postgres if I needed transactions across collections or heavy analytical queries — for example leaderboards and per-tag statistics — because MongoDB's aggregation for that is more awkward.
4. Walk me through what happens when a user clicks Submit.
Use flow 7.4 verbatim. Emphasise: the submission row is written as pending before Judge0 is called, so an attempt is never lost; hidden test cases are used, never the visible ones; the batch is submitted in one call and polled until every status_id > 2; runtime is summed and memory is the peak; then the row is updated with the verdict.
5. Is your API RESTful?
Mostly. Resources are nouns, HTTP verbs are used correctly (GET/POST/PUT/DELETE), and status codes are meaningful — 201 for creation, 401 for auth failure, 404, 409 for a duplicate video. Where it deviates: some paths are verb-y (/problem/getAllProblem should just be GET /problems), and some errors return plain strings instead of JSON. I would normalise to plural noun resources and a consistent JSON error envelope.
6. How would you scale this to 100,000 users?
Four layers. Database: pagination plus indexes on difficulty and tags; read replicas. Caching: Redis for the problem list and individual problems, which are read-heavy and rarely change. Judging: move it out of the request path into a BullMQ worker pool with Redis, returning a submission id immediately and pushing the verdict over WebSocket — right now a submission holds an HTTP connection open for seconds. Infrastructure: the API is stateless (all state is in Mongo/Redis), so I can run N instances behind a load balancer with no sticky sessions. I would also self-host Judge0 rather than depend on RapidAPI rate limits.
7. What was the hardest part?
The Judge0 integration, because it is asynchronous. Submitting returns tokens, not results, so I had to build a polling loop with a correct termination condition — status_id > 2 means finished regardless of verdict. I also hit a subtle bug where my waiting() helper wrapped setTimeout without a Promise, so await did not pause and I was hammering the API. That taught me that await only works on thenables.

B. Authentication & security

8. How does authentication work end to end?
On login the server verifies the password with bcrypt.compare, signs a JWT containing _id, emailId and role with a one-hour expiry, and sets it as a cookie. The browser then attaches that cookie automatically on every request because axios is configured with withCredentials:true and CORS allows credentials. On protected routes userMiddleware verifies the signature and expiry, confirms the user still exists, checks the Redis blocklist, and attaches the user document to req.result.
9. JWT is stateless — so how does logout work?
That is exactly the problem. You cannot un-issue a signed token. So on logout I write the token into Redis as token:<jwt> = "Blocked" and userMiddleware checks that list on every request. The elegant part is expireAt(key, payload.exp): the Redis TTL is set to the token's own expiry, so once the JWT would be rejected anyway the blocklist entry evicts itself. The blocklist is self-cleaning and can never grow unbounded.
10. JWT vs sessions — why did you pick JWT?
Statelessness and horizontal scaling: any API instance can verify a token with just the secret, no shared session store and no sticky sessions. The trade-off is revocation, which sessions get for free — and I paid for that with the Redis blocklist, which is arguably a hybrid. If I were starting again for a single-server app, sessions would honestly be simpler.
11. Cookie or localStorage for the token — and why?
Cookie. localStorage is readable by any JavaScript on the page, so one XSS flaw leaks the token permanently. A cookie can be marked httpOnly, which makes it invisible to JavaScript entirely. Being honest: my implementation does not set httpOnly, secure or sameSite — that is the first thing I would fix. With sameSite:'strict' you also get CSRF protection, which is the cookie approach's main downside handled.
12. Can a user make themselves an admin?
Not through /user/register — the controller hardcodes req.body.role = 'user' after validation, so a posted role field is overwritten. That is a mass-assignment defence. They also cannot forge a token because they do not have JWT_KEY. The real weakness is different: adminMiddleware reads the role from the token payload instead of the freshly-loaded database record, so a demoted admin keeps admin access until their token expires.
13. Why bcrypt and not SHA-256?
SHA-256 is designed to be fast, which is exactly wrong for passwords — an attacker with a leaked table can try billions of guesses per second on a GPU. bcrypt is deliberately slow via a configurable cost factor (10 here = 1024 rounds) and auto-generates a per-password salt embedded in the hash, which defeats rainbow tables and makes identical passwords hash differently.
14. What is in your JWT payload, and is that safe?
_id, emailId, role, plus iat and exp. It is safe in the sense that nothing secret is there — a JWT payload is base64-encoded, not encrypted, so anyone holding the token can read it in jwt.io. The signature protects integrity, not confidentiality. That is why the password hash is never in there.
15. How do you stop users seeing the hidden test cases?
getProblemById uses a Mongoose projection — .select('_id title description difficulty tags visibleTestCases startCode referenceSolution') — and hiddenTestCases is simply not in the list, so it never leaves the database layer. That projection is the security boundary of the whole judging system. The flaw I would fix: referenceSolution is in that list, so a user can read the answer in DevTools before solving.
16. Someone bypasses your React admin check with DevTools. What happens?
Nothing useful. The client-side guard in App.jsx is purely UX — it hides buttons and redirects. Every admin endpoint is independently protected by adminMiddleware on the server, which verifies the token and the role. Client-side checks are convenience; server-side checks are security.

C. Backend

17. What is middleware in Express?
A function with signature (req, res, next) that sits in a chain between the request and the route handler. It can inspect or mutate req/res, end the request, or call next() to pass control on. Order matters — cookieParser must run before any auth middleware that reads req.cookies. My auth middleware also uses it to attach the loaded user to req.result so controllers do not each refetch it.
18. Why Promise.all in the boot sequence?
To connect MongoDB and Redis in parallel rather than sequentially, roughly halving startup time, and to fail fast if either rejects. Crucially, app.listen only runs after both resolve, so the server never accepts traffic it cannot serve.
19. What is populate() and what does it cost?
Mongoose's application-level join. problemSolved stores only ObjectIds; populate issues a second query to the problems collection and substitutes the real documents. The cost is that extra round trip — it is not a database-level join like SQL, so on large result sets it can become an N+1-style problem. I limit the damage with select so only four fields come back.
20. Why the compound index on submissions?
The hot query is Submission.find({userId, problemId}) for submission history. Without an index MongoDB does a collection scan; with {userId:1, problemId:1} it does an index scan straight to the matching range. Because of the prefix rule that index also covers queries on userId alone, but not problemId alone — if I needed that I would add a separate index.
21. Explain the Mongoose hook in your user model.
A post('findOneAndDelete') hook that deletes every submission belonging to the removed user. MongoDB has no foreign keys or ON DELETE CASCADE, so cascade is an application concern. The important detail is that hooks are bound to specific query methods — findByIdAndDelete internally calls findOneAndDelete so the hook fires, but deleteMany() would bypass it entirely.
22. Why runValidators: true?
Mongoose runs schema validators on save() but skips them on update queries by default, for historical reasons. Without that flag, findByIdAndUpdate would happily write difficulty: "impossible" straight past the enum. I pair it with new: true so the updated document is returned rather than the original.
23. How do you run untrusted user code safely?
I do not run it myself — that is the whole point. Executing arbitrary user code in my Node process would be a remote code execution vulnerability. I delegate to Judge0, which runs each submission in an isolated container with CPU time, wall-clock and memory limits, and no network access. My server only ever handles strings.
24. What is status_id and why > 2?
Judge0's verdict code. 1 is In Queue and 2 is Processing — both non-terminal. Everything from 3 up is a finished state: 3 Accepted, 4 Wrong Answer, 5 TLE, 6 Compilation Error, 7–12 runtime errors. So status_id > 2 means "this submission has finished, whatever the outcome", which is the correct condition to stop polling, and status_id === 3 means the test case passed.
25. What happens if Judge0 is down?
Honestly, not enough. submitBatch catches the axios error, logs it and returns undefined, so the next line throws on .map() and the outer catch returns a 500. Meanwhile the submission row stays stuck at pending. What it should do: mark the submission as error with a clear message, add retries with exponential backoff, and a circuit breaker so I stop hammering a dead dependency.
26. Why create the submission before judging it?
Write-ahead. Judging takes seconds and depends on a third party. Persisting the attempt as pending first means a crash, timeout or restart never loses the user's submission, and the row can be reconciled later. It is the same reasoning behind a job queue: record intent, then do the slow work, then record the outcome.
27. Explain the Cloudinary signed upload.
The naive approach — upload to my Express server, which forwards to Cloudinary — doubles bandwidth and ties up a single-threaded Node process for minutes on a 100 MB file. Instead my server generates an HMAC signature over the upload parameters using the API secret and returns it to the browser. The browser uploads directly to Cloudinary with that signature; Cloudinary recomputes the HMAC and rejects anything that does not match. The secret never leaves my server, the file never touches it, and I still control the upload path because public_id and timestamp are part of the signed payload. Afterwards the client tells my server where it landed, and my server verifies with Cloudinary's Admin API before saving the metadata.
28. Why is the AI limited to DSA?
A system instruction that injects the current problem's title, description, test cases and starter code, then sets explicit rules: act as a tutor, give hints without spoiling the solution, explain complexity, and politely refuse anything unrelated. That is prompt engineering as a product decision — it keeps the assistant useful and on-task, and stops the endpoint being abused as a free general-purpose chatbot on my API quota.

D. Frontend

29. Why Redux Toolkit, and why only for auth?
Auth is genuinely global — route guards, the navbar and multiple pages all read it, and prop-drilling it would be painful. RTK gives me createAsyncThunk, which auto-generates pending/fulfilled/rejected actions so every async call has a proper loading and error state, plus Immer so I can write mutable-looking reducers safely. Everything else — problem lists, submissions, editor state — is local to one screen, so it stays in useState. Putting server data in Redux for its own sake just adds boilerplate; these days I would reach for TanStack Query for that.
30. What does createAsyncThunk actually do?
It takes a type prefix and an async function and generates three action types — pending, fulfilled, rejected — dispatching them automatically around the promise. I handle all three in extraReducers, which is what makes the loading spinner and error message reliable. rejectWithValue lets me control the error payload rather than getting a raw Error object.
31. Why extraReducers and not reducers?
reducers defines actions the slice owns and generates creators for them. extraReducers responds to actions defined elsewhere — and thunk-generated actions are exactly that. My reducers object is empty because every state change in this slice is driven by an async thunk.
32. You mutate state in your reducers. Isn't that illegal in Redux?
It looks illegal but is not. Redux Toolkit wraps every reducer in Immer, which hands you a draft proxy, records the mutations you perform on it, and produces a brand-new immutable state object. You get mutable ergonomics with immutable guarantees. Outside RTK, that same code would be a genuine bug.
33. How does the app survive a page refresh?
Redux state is in memory and dies on refresh, but the cookie survives. On mount, App.jsx dispatches checkAuth, which calls GET /user/check; the middleware validates the cookie and the route returns the user, rehydrating Redux. Crucially, while that request is in flight loading is true and the app renders only a spinner — otherwise the first render would see isAuthenticated:false and briefly redirect a logged-in user to the signup page.
34. Why React Hook Form instead of controlled inputs?
Performance and ergonomics. Controlled inputs re-render the component on every keystroke; RHF keeps values in refs so the field stays uncontrolled and typing causes zero re-renders — it only re-renders when validation state changes. It also handles nested field arrays cleanly, which I needed for the dynamic test-case rows in the admin panel.
35. Explain useFieldArray.
It manages an array of form fields at runtime — append, remove, and a fields array to map over. In the admin panel it lets an admin add or delete any number of visible and hidden test cases. Registration uses a dotted path like visibleTestCases.0.input, which RHF assembles into a nested array on submit. I key each row by field.id, not the array index, because index keys corrupt state when a middle row is removed.
36. Why is your API call inside useEffect and what does the dependency array do?
Fetching is a side effect, so it belongs in useEffect rather than the render body — rendering must stay pure. The dependency array controls re-runs: [] is once on mount, [problemId] re-fetches when the route parameter changes, and omitting it entirely runs after every render, which is almost always an infinite loop. A returned function is the cleanup — I use that in the video player to remove the timeupdate listener on unmount.
37. When do you use useRef instead of useState?
When the value must persist across renders but changing it should not trigger one, or when I need a direct handle on a DOM node. I use it three times: the Monaco editor instance, the <video> element so I can call .play()/.pause(), and a sentinel div at the bottom of the chat that I scrollIntoView on new messages.
38. Why does Vite start so much faster than CRA?
In development Vite does not bundle at all — it serves your source as native ES modules and lets the browser request them on demand, transpiling per file with esbuild (Go, very fast). Webpack/CRA builds the whole dependency graph before serving the first byte, so startup time grows with project size. For production Vite bundles with Rollup, where bundling is actually worth it.
39. What is StrictMode and why did you see double API calls?
A development-only wrapper that intentionally double-invokes renders and effects to surface impure logic and missing cleanup functions. It is why an effect that fetches on mount can fire twice in dev. It does not happen in production builds, and the correct response is to make effects idempotent and add cleanup rather than to remove StrictMode.
40. What would you do differently if you rebuilt this?
Four things. TypeScript across both sides — most of my bugs were shape mismatches, like three different spellings of "cpp", which types would have caught at compile time. Judging as a background job with BullMQ and WebSocket updates instead of holding an HTTP connection open. Tests from day one, at least Supertest coverage on auth and submission. And a centralised error handler with a custom error class, instead of repeating try/catch and ad-hoc string errors in every controller.
